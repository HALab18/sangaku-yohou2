# 登山指数・計算方法の基準表

## 登山指数 A/B/C の判定基準

登山指数は「その時間帯に登山行動が適しているか」を表す指標。
**主判定に使うのは稜線風速と降水量の2項目**で、そのあとに**降格条件**（下記）を安全側にのみ重ねる。
3時間ブロックごとに以下を判定し、**最悪値**をそのブロックの指数とする。
日別指数は行動時間帯（5〜16時）のブロックの最悪値。
閾値は**予報対象日の月と山頂気温**で夏山／冬山・残雪期モードを自動切替する。

**夏山モード（6月〜10月）**

| 項目 | A（適） | B（注意） | C（不適） |
|---|---|---|---|
| 稜線風速 | < 10 m/s | 10〜15 m/s | ≥ 15 m/s |
| 降水量(3h) | < 1 mm | 1〜5 mm | ≥ 5 mm |

**冬山・残雪期モード（11月〜5月）**

| 項目 | A（適） | B（注意） | C（不適） |
|---|---|---|---|
| 稜線風速 | < 8 m/s | 8〜12 m/s | ≥ 12 m/s |
| 降水量(3h) | < 1 mm | 1〜3 mm | ≥ 3 mm（降雪リスク） |

- **雷（CAPE）は判定に使わない**。雷は局地性が高く「行動が適しているか」とは性質が異なるため、
  指数には含めず「発雷リスク」として独立表示する（下記）。
  景色（眺望）も独立した情報として扱い、指数には混ぜない。
  利用者が「登れるか／雷は／景色は」をそれぞれ判断できる構成にするため。
  体感温度は独立表示を続けつつ、凍傷リスク域（-20℃以下）では降格条件 D2 として指数にも効かせる。
- **降水確率は判定に使わない**（表には参考値として表示のみ）。判定に使うのは実測降水量(3h)
- **判定材料が無い時間帯・日は指数を出さず「-」**（稜線風・降水がどちらも欠測の場合）。
  景色（眺望）も材料が無ければ「-」。欠測を A（登山適）・◎（展望良好）として表示すると
  「データが無い」が「条件が良い」に化け、安全と逆方向に誤解させるため。
  降水の合計は「有効値ゼロなら None」で扱い、実測の 0mm と欠測を区別する
- 指数の意味: A=登山適 / B=要注意(経験者向き・行程短縮検討) / C=登山不適。
  **指数の下には「その評価を決めた条件」を併記する**。主判定で決まったなら
  **風／降水**、降格条件で下がったなら **低体温／体感／視界**。
  同じ B でも「風が強い」と「雨」では取るべき行動が違う（行程短縮か中止か）ため、
  主判定側にも名前を出す。A のときは説明する対象が無いので何も付けない。
  - 風と降水が**同じ評価で並んだら「風・降水」と両方**出す。片方だけ書くと
    もう片方は基準内だったと誤解される。
  - 降格条件が主判定と**同じ評価に留まるときは降格せず、主判定の理由を残す**
    （降格は厳密に悪いときだけ採用する。同着で上書きすると、しきい値を超えた風という
    一次的な事実が理由から消える）。
  - 語は「雨」ではなく**「降水」**。降水量は水換算で、冬は同じ数値が雪を意味する
    （雨か雪かは別途 0℃高度から判別して表示している）。
- てんきとくらす等の「登山指数」と似た思想だが独自基準。絶対視しないこと。

## 降格条件（主判定のあとに安全側にのみ重ねる）

風と降水だけでは、**実際に人が死ぬ条件が A のまま出てしまう**ため追加した。
材料が欠測の条件はスキップする。良い方向には決して倒さない。

| ID | 条件 | 降格先 | 根拠 |
|---|---|---|---|
| D1 | 気温 ≤ 10℃ **かつ** 3h降水 ≥ 1mm **かつ** 稜線風 ≥ 8m/s | B（風 ≥ 12m/s なら C） | 湿潤低体温。2009年トムラウシ（7月・気温8〜10℃・風20m/s・雨・8名死亡）の型。**夏でも起きるので季節に依存させない** |
| D2 | 体感温度 ≤ -20℃ | B | 露出部の凍傷リスク域 |
| D2' | 体感温度 ≤ -30℃ | C | 凍傷が短時間で発生。行動継続は不可 |
| D4 | 視程 < 200m **かつ** 稜線風 ≥ 10m/s | **C** | 地吹雪・ホワイトアウト＋強風で行動困難 |

- 入力はブロック内の**安全側代表値**（気温=最小 / 風=最大 / 降水=合計 / 視程=最小）。
- **D4 の降格先が B ではなく C なのは意図的**。風10m/s は夏（閾値10）でも冬（閾値8）でも
  主判定で既に B 以上になるため、「最低B」にすると D4 は一度も効かない死んだ条件になる（実装時に判明）。
- D2 の体感温度は上限ガード適用後の値。10℃超では気温がそのまま返るので夏に誤発火しない。
- D3（突風による降格）は**採用していない**。突風は地上10mの値で稜線風と高度が違うため、
  そのまま閾値判定に使うと高度の不整合を判定に持ち込むことになる。表示と注記のみで扱う。
- find（山さがし）は視程を取得しないため **D4 だけは計算できない**。主判定＋D1＋D2 を併記する。

## 夏冬モードの切替

```
冬モード = (月が 11〜5月) または (日最高山頂気温 < 0℃) または (日最低山頂気温 < -3℃)
```

- 月ベースを基本に、**寒い日だけ冬側へ倒す**。冬→夏に戻す条件は設けない（安全側のみ）。
- 純粋な気温ベースにしてはいけない。「山頂気温が0℃未満なら冬」だけにすると
  5月の北ア（日中+2〜5℃）が夏モードに落ち、現行より甘くなる。
- 気温は**行動時間帯（5〜16時）**のもので判定する。1日全体の最低気温を使うと、
  3000m級は真夏でも明け方に-3℃を下回ることがあり（実測: 富士山の8月）、
  行動時間帯は5℃前後なのに日中の判定まで冬モードに倒れる。
- これで北海道の9月下旬・3000m級の9月下旬〜10月が冬モードに入る（月だけの切替では最大の穴だった）。
- モードは**日単位**で決め、その日の全ブロックに同じ閾値を使う（同一日内で基準がぶれないように）。
- 山域・緯度による個別調整はしない（気温が緯度・標高を代理している）。
  冬は同じ風速でも危険度が大きく上がるため閾値を8/12m/sに引き下げている。

## 夕方急変の警告フラグ（⚠夕方）

行動時間帯外の 17〜20時 が次のいずれかに該当する場合、
日別指数（A/B）は変えずに **「⚠夕方」警告** を付記する。

- 風・降水で **C 相当**
- **発雷リスクが「注意」以上**（レベル2以上。雷は指数に含めないぶんここで拾う）

下山遅れ・テント泊・ご来光待ちで夕方以降も行動する場合の注意喚起。
日別指数が既に C の日は付けない（すでに登山不適と示せているため）。

**雷の条件には山頂格子の CAPE を使う**（周辺最大ではない）。周辺最大を入れると夏は周辺の
どこかが必ず 1000 J/kg を超えるためフラグがほぼ毎日立ち、日を区別できなくなる
（実測: 槍ヶ岳で 11日中 1日 → 10日）。毎日出る警告は無視されるので安全と逆方向に働く。

## 夜間急変の警告フラグ（⚠夜間）

**当日21時〜翌朝5時**が風・降水で **C 相当**なら「⚠夜間」を付記する。日別指数は変えない。

- 行動時間帯（5〜16時）にも夕方（17〜20時）にも入らないため、**この帯はこれまで完全に無評価**だった。
- 冬型では風のピークが夜間〜早朝に来ることが多く、テント泊・小屋泊・
  早発ち（アルパインスタート）で最初に効く。
- 発雷は条件に入れない（夜間のテント泊で効くのは風）。
- 日別指数が既に C の日は付けない（⚠夕方と同じ）。
- 最終日は翌日データが無いので 21〜23時のみで判定する。

## 稜線風の算出

Open-Meteo の気圧面風速を山頂標高で線形補間。10m風（地形に沿った地上風）より
気圧面風のほうが稜線上の実勢に近い。

| 気圧面 | 標準高度(m) | 対応する山の例 |
|---|---|---|
| 925hPa | 760 | 筑波山、高尾山 |
| 900hPa | 990 | 泉ヶ岳 |
| 850hPa | 1460 | 丹沢、蔵王、谷川岳 |
| 800hPa | 1950 | 月山、那須、美ヶ原 |
| 700hPa | 3010 | 北アルプス主稜線、八ヶ岳上部 |
| 600hPa | 4200 | 富士山頂 |

補間に使う面は**その時刻に実際に値がある面**から毎回選ぶ（標高から面のペアを1回だけ
決め打ちにはしない）。気圧面のラインナップはモデルで違い、MSM（予報の前半）は
6面すべて配信するが、**GSM（予報の後半）は 900hPa と 800hPa を配信しない**ため。
決め打ちだと、その2面に依存する標高帯の山が GSM 期間に補間できなくなる。
なお **MSM→GSM の切替が何日目かは固定ではない**（モデルのラン時刻で前後する）。
境目が要るときは `model_switch()` / `modelSwitch()` で実データから出すこと。
上下に面が無い（925hPa より低い・600hPa より高い）場合は最寄りの面の値をそのまま使う。

風向は角度なので同じ式では補間できない。**値のある面のうち標準高度が山頂標高に最も近い面**の
風向をそのまま採用する。

面が減るぶん、GSM 期間は風をやや弱めに見積もる傾向がある（北アルプス級で平均 -1.2m/s）。
欠けた面を別モデルの値で埋める案は実測で誤差が悪化したため採らず、補正せずに開示する方針
（詳細は DEVLOG と `docs/find-score.html`）。

### 地上10m風を内挿の最下点に置く

気圧面の最下端は 925hPa（標準高度760m）なので、旧実装ではそれより低い標高がすべて
「最下面の生値」にクランプされていた。つまり**標高300mの里山に上空760mの風が出る**
（実測: 仙台市街で 925hPa 7.5m/s に対し地上10m風 0.6m/s）。
内蔵DBでは**標高100〜760mに76座（12.6%）**あり、この帯が丸ごと過大評価になっていた。

そこで**地上10m風を「高度10mの面」として `pts` の先頭に足し、他の気圧面と同じ内挿に乗せる**
（`SURFACE_WIND_M = 10`）。標高760m未満は地上風と925hPaの間で内挿される。

```
pts = [[10, 地上10m風], [760, 925hPa], [990, 900hPa], [1460, 850hPa], ...]
```

- 旧実装にあった「標高100m未満だけ地上風に切り替える」分岐は**廃止**した。
  100m ちょうどでの不連続な段差も同時に消える（実測: 衣張山122m で最大 13.3 → 5.9 m/s）。
- 760m以上の山は挙動が変わらない（実測で筑波山877m・大山1252m とも変化なし）。
- 列見出しは標高100m未満のみ「地上風(10m)」（内挿値の実体がほぼ地上風になるため）。
  100〜760m は「稜線風」のまま、地点メタに内挿している旨の注記を出す。

この算出の実装は **`logic.js`（interpWind）と `scripts/mountain_weather.py`（interp_wind）の
2箇所だけ**（ver 2.30β で一本化。`index.html` と `docs/find.html` は `logic.js` を読む）。
同一であることは `references/logic_cases.json` の入出力表で機械的に検証している
（`python scripts/test_logic.py && node scripts/test_logic.js`）。

## 体感温度

**豪州気象局の Apparent Temperature（Steadman）** で算出する。気温・風・湿度の3つを使う。

```
e  = (RH/100) × 6.105 × exp(17.27×T / (237.7+T))   … 水蒸気圧(hPa)
体感温度(℃) = T + 0.33×e − 0.70×稜線風速(m/s) − 4.00
（T = 山頂気温[℃]、RH = 相対湿度[%]）
```

### なぜ風冷指数（JAG/TI式）をやめたか

JAG/TI は **気温10℃以下・風速4.8km/h以上** でのみ有効な式で、寒冷時の顔面の熱損失に
較正されている。式の構造上 `+0.3965×T×V^0.16` の項が気温に比例して増えるため、
**約22℃を超えると気温より高い値を返す**（気温25℃・風14m/sで25.9℃）。

かといって10℃で打ち切って気温をそのまま返すと、今度は
**10〜22℃の帯で冷却がまったく表現されない**うえ、境界で不連続になる。

| 条件 | JAG/TI素の式 | 10℃で打切 | Apparent Temperature |
|---|---|---|---|
| 飯豊山 13.8℃・17.0m/s・RH95% | 10.3℃ | **13.8℃** | **3.0℃** |
| 10.0℃・14m/s・RH95%（境界の直下） | 5.5℃ | 5.5℃ | 0.0℃ |
| 11.0℃・14m/s・RH90%（境界の直上） | 6.8℃ | **11.0℃** | 1.1℃ |
| −15℃・12m/s・RH70% | −27.8℃ | −27.8℃ | −27.0℃ |
| 30℃・2m/s・RH90% | 32.5℃（破綻） | 30.0℃ | 37.2℃ |

打切り方式は気温が10.0→11.0℃と1℃上がるだけで体感が5.5→11.0℃と跳ね上がる。
どちらも登山者に誤った印象を与えるため、全温度域で有効な AT に置き換えた。

- **寒冷域では JAG/TI とよく一致する**（−15℃・12m/s で −27.8 vs −27.0）ので、
  冬の数値の意味は実質変わらない。山岳では平均2〜6℃低め、夏の低山では高めに出る。
- **高温多湿では体感が気温を上回る**（30℃・RH90%・微風で37.2℃）。湿度で熱が逃げないことを
  表す正しい挙動なので、`min(式の値, 気温)` のような抑えは入れない。
- **日射は考慮しない**（日なたでは実際より涼しく出る）。
- 風は**稜線風**（山頂標高）を渡す。式は地上10m風を前提にしているが、登山者が受けるのは
  稜線の風なのでこちらを使う（JAG/TI 時代と同じ扱い）。
- **材料が1つでも欠測なら `None`（「-」表示）。** 気温をそのまま返すと、他の欠測が全て「-」
  なのにこの列だけ数値が出て、欠測だと気づけない。
- **表示の桁数は必ず気温と揃える（どちらも小数1桁）。** 気温が小数1桁・体感が整数だと、
  値が同じでも `12.8℃ → 体感13℃` となり、**丸めだけで「風が吹くと暖かくなる」表示が生まれる**。
  実際に飯豊山の予報で発生した（整数表示なら全域スキャンで1290通りが逆転、小数1桁なら0通り）。

湿潤時（雨・汗濡れ）は式の値よりさらに下がるので注意（「濡れ注意」の印で補う）。
- **風が欠測なら `None`（「-」表示）。** 旧実装は気温をそのまま返しており、
  他の欠測が全て「-」なのにこの列だけ数値が出て、欠測だと気づけなかった。
- 体感温度は独立した参考値だが、凍傷リスク域では降格条件 D2 として指数にも効かせる。
- **「濡れ注意」の印**: 3h降水0.1mm以上＋**気温15℃以下**＋稜線風8m/s以上。
  気温の上限が D1（10℃）より高いのは意図的で、**表示専用**の値。
  **Apparent Temperature は「乾いた状態」の式で、濡れた衣服の蒸発冷却を含まない。**
  体感の数字そのものはこの帯でも冷えを表すが（飯豊山の気温13.8℃・稜線風17m/s は
  AT で約2〜3℃）、濡れるとそこからさらに下がる。数字が一桁台に見えても致命的に
  ならない帯こそ濡れ＋風の低体温が起きるので、印で補う。
  なお**旧実装（風冷指数 JAG/TI）は10℃超で適用外になり「体感＝気温」を返していた**ため、
  同じケースが体感13.8℃と表示されていた。AT への置換でこの欠陥自体は解消済み。
  判定（D1）のしきい値は10℃のまま——15℃に上げても4山×11日で判定の変化はゼロで、
  主判定の風・降水が既に拾っていた。
- **相対湿度は条件に使わない**——実測で山頂のRHは中央値89〜91%、
  95%以上が23〜40%の時間を占め、視程45kmの快晴でも95%を超えるため、印が常時点灯してしまう。

## CAPE（対流有効位置エネルギー）の目安

| CAPE (J/kg) | 雷雨の可能性 |
|---|---|
| < 500 | 低い |
| 500〜1000 | 雷雨の可能性あり（夏山午後は特に注意） |
| 1000〜2500 | 雷雨発生しやすい |
| > 2500 | 激しい雷雨・危険 |

CAPEが低くても上空寒気やトリガー次第で雷は起きる。夏山では「13時までに下山開始」が原則。

### CAPE は山頂ではなく周辺の最大値を採る

山岳雷を起こすのは**谷や麓の湿った下層気塊が地形に持ち上げられたもの**で、山頂格子の CAPE は
その気塊を表さない。実測（槍ヶ岳・11日間）:

| 取得地点 | CAPE 最大 |
|---|---|
| 山頂格子 (3180m) | 1340 J/kg（＝発雷リスク lv2「注意」） |
| 松本 (610m・約25km) | 3050 J/kg（＝lv3「高い」） |

264時刻中 **172時刻（65%）で麓が山頂を上回り**、最大差 2410 J/kg。山頂だけ見ると
**1〜2段階低く表示される**。そこで山頂＋東西南北 ±0.25度 の計5地点を取り、
同時刻の**最大 CAPE と、その地点の CIN** を使う。
Open-Meteo はカンマ区切りのマルチ地点に対応するのでリクエスト数は増えない。

**ただし ⚠夕方フラグの雷条件には山頂格子の値を使う**（上記「夕方急変の警告フラグ」参照）。

## 発雷リスク 4段階（詳細表の表示専用・A/B/C判定には不使用）

CAPE（対流の燃料）だけでは発雷は判断できないため、CIN（上昇を抑える蓋）と組み合わせる。
CLI(`lightning_risk`)とWeb(`lightningRisk`)で同一ロジック。

**CAPEで基準段階を決める**（区切り 500/1000/2500。上記「CAPEの目安」と一致させてある）

| 表示 | CAPE (J/kg) |
|---|---|
| ⚡ 低 | < 500 |
| ⚡⚡ やや注意 | 500〜1000 |
| ⚡⚡⚡ 注意 | 1000〜2500 |
| ⚡⚡⚡⚡ 高い | ≥ 2500 |

**CINで段階を下げる**（下げる方向にのみ効かせる）

| \|CIN\| (J/kg) | 補正 |
|---|---|
| ≥ 100 | 2段下げ（強い蓋） |
| 50〜100 | 1段下げ |
| < 50 | 補正なし |

最後に0〜3にクランプ。CAPEが取得できない場合は「-」表示。

- ブロック集計は **CAPE=最大値 / CIN=絶対値の最小値（蓋が最も薄い時刻）** で安全側に倒す。
- 蓋が薄いことを理由に段階を**上げない**。Open-Meteoの`convective_inhibition`は絶対値で返り、
  実データでは中央値1〜15・約半数が0（蓋なしが既定状態）のため、上げる補正を入れると
  ほぼ全時刻が上振れして段階が機能しなくなる。
- 表示は絶対値ではなく慣例に合わせた負値表記（例: `CAPE 820 / CIN -40`）。
- あくまで参考表示。雷は局地現象であり発生地点・時刻の予測はできない。

## 景色（眺望）◎/○/△/✕

**山頂付近の雲・視程・降水**の3つを組み合わせた4段階。
山頂標高がかかる雲層（<2000mの山=下層雲/中層雲、≥2000mの山=中層雲）を「山頂のガス」、
山頂より下の層の雲を「雲海の可能性」として判定する。

| 判定 | ラベル | 条件 |
|---|---|---|
| ✕ | 雨 / 濃霧 | 3h降水≥1mm（=雨） / 視程<2km・山頂レベル雲量≥80%（=濃霧） |
| △ | ガス | 山頂レベル雲量≥50% または 視程<10km |
| ○ | 良好 | 山頂レベル雲量<50% |
| ◎ | 展望良好 | 山頂レベル雲量≤20% かつ 視程≥20km（視程欠測時は相対湿度<95%） |
| (雲海) | - | 山頂より下の雲量≥60% かつ 山頂レベル≤30% → ○/◎に付記 |

- **視程が欠測のときは相対湿度で裏を取る**（RH ≥ 95% なら ◎ を出さず ○ 止まり）。
  旧実装は `vis==null || vis>=20000` で、視程が取れていなくても雲量が少なければ ◎ を出しており、
  「データが無い」が「展望良好」に化けていた。欠測を好条件に倒さない原則の唯一の破れだった。
  RH の閾値が 95% なのは、実測で山頂の RH が中央値 89〜91% と高めに出るため（90%では半数が該当する）。
- **視程は景色を算出するための内部要素**であり、単独の評価項目としては表示しない。
  詳細表からは視程列を廃し、景色セルの補足情報として併記する
  （Web＝アイコン＋記号＋ラベルの下段に小さく／CLI＝`◎ 展望良好 (視程25km)` の1行）。
  利用者は最終的な「🏔 景色」の4段階を見れば判断できる。
- Web版は4段階を SVG アイコンで表示する（`#view-ex/ok/so/ng`。viewBox 32×32・表示21px）。
  **面塗りの山＋線画の天候**で構成し、山は4種共通の `#view-mt`（二峰・左が高い／右斜面に
  白20%の陰影／雪渓2つ）を `<use>` で共有する。山の塗りは `currentColor` なので、
  使用側の判定色クラス（`.v-ex/.v-ok/.v-so/.v-ng`）がそのまま山の色になる（色定義は1箇所）。
  差し替えるのは太陽・雲・ガス・雨だけ。◎○は天候を山の後ろ、△✕は前に描いて奥行きを出す。
  グラデーション・フィルタは使わず fill と stroke のみ。
  色覚特性に配慮し、アイコンだけでなく ◎○△✕ の記号とラベルを必ず併記する。
  `index.html` と `docs/how-it-works-web.html` にスプライトの実体があるので**両方そろえる**。
- 日別サマリの「景色(朝)」は4〜8時の最良値（ご来光・朝の展望の目安）。
  併記する視程は**採用した時刻そのもの**の値（ブロック最小値ではない）
- 雲量バンド（下層<2km/中層2〜7km/上層>7km）は近似。雲頂・雲底高度は数値予報では正確に
  出ないため、稜線ぴったりの雲（滝雲・ガスの湧き）は判定できない
- 低山（<2000m）の谷霧・盆地霧は表現できない
- 上層雲(すじ雲等)は眺望を妨げないため判定に含めない（ご来光の焼けはむしろ絵になる）

## 直近実況（過去3日）の表示

予報とあわせて直近3日のモデル解析値（実況相当）を取得し、予報の前に表示する。
直近の降水・降雪・積雪深の経過を、登山道の状態（ぬかるみ・増水・残雪等）を
利用者自身が見立てるための材料として提供する。
観測所の実測ではないため「モデル解析値」と明記する。
**A/B/C判定には使わない**（表示のみ）。断定的なコンディションのコメントは付けない。

## 積雪の表示

- hourly `snow_depth`（積雪深, m→cm表示）と daily `snowfall_sum`（新雪, cm）を使用
- 表示形式「85cm(+12)」= 積雪深max 85cm・新雪12cm。3時間詳細はブロック内の値
- 取得期間内に積雪・降雪が一度も無い場合は積雪列そのものを省略する（夏山の表を簡潔に保つ）
- A/B/C判定には組み込まない（降雪は降水量として間接的に反映される）

## 横断検索の「日和スコア」（docs/find.html 専用の簡易指標）

「その日に天気の良さそうな山をまず見つけたい」ための逆引きページ（docs/find.html、
生成: scripts/gen_find.py）で使う**簡易スクリーニング指標**。上記 A/B/C の正式判定とは
**別物**であり、CLI/Web 共通の判定ロジックには一切影響しない（規約3の対象外）。

- 目的: エリア内の多数の山を**バッチ取得**し、相対的な良し悪しで並べる「ふるい」。
  1回の取得は最大50座（負荷抑制のため50座ごとに分割・直列取得）。
  1チャンクにつき気象庁モデル＋補完（降水確率・日照の2変数）の**2リクエストを並行**で投げる。
- 対象期間: **今日〜6日先の7日間**（`FIND_DAYS`。日数の変更はこの定数1箇所で行う）。
  気象庁モデルは天気・降水・気圧面風・積雪を11日ぶん配信するが、スコアの主要素である
  `sunshine_duration` だけは MSM 期間ぶんしか来ず、4日目以降は 7:00〜15:59 が丸ごと欠測になる。
  そこで**日照だけ**を汎用Forecast API（ベストマッチ合成）から `sunshine_supp` という別名で
  取得して補完し、期間を7日に延ばした。1〜3日目は気象庁モデルの日照を優先する
  （基本はMSM/GSM、足りないところだけ他モデル）。補完した日は表の日照に `*` 印＋表下に注記を出す。
  `FIND_DAYS <= JMA_DAYS(10)` は不変条件（山名リンク先が `../index.html#山名/日付` のため）。
  日付選択肢は4日目以降に「参考」を付す（日照が別モデル由来・稜線風が粗い・予報誤差が大きい、と
  性質が変わるため。日照の `*` は検索後にしか見えないので、性格は日付そのものに出す）。
- 集計は**すべて hourly 値**を 7:00〜15:59（登山コアタイム9時間）で集計する（daily は積雪のみ）。
- スコア（0〜100・減点方式）の重み順:
  1. **晴天度（-28）**: 日照率 = `sunshine_duration` 合計 / (9h×3600s) を主指標。
     気象庁モデルの日照を優先し、無ければ補完した `sunshine_supp` を使う（`sunAlt=true`）。
     どちらも**窓9時間ぶんがそろっている時だけ採用**する（部分欠測の合計をそのまま日照率に
     すると「3時間しか来ていない日＝日照率33%」となり実際より悪く採点してしまう）。
     両方とも取れない時のみ `weather_code` で代替。雨雪雷の天気コードは軽く上乗せ減点。
  2. **降水量（-30）**: `precipitation` の合計。`min(合計,10)/10×30`。
     気象庁モデルに降水確率が無いため、旧「確率-10＋量-20」を量に一本化した。
  3. **稜線風（-32）**: 地上10m風と気圧面（925〜600hPa）から山頂標高に線形補間した値の最大。
     **夏は6→18m/s、冬は4→12m/s** で減点が0から最大に達する（冬は正式判定の閾値8/12m/sに合わせて前倒し）。
     **その時刻に実際に値がある気圧面だけ**を使って補間する（`interpWind`）。配信される面は
     モデルで違い、MSM は6面すべて、GSM は 900hPa と 800hPa を配信しない。標高から面のペアを
     決め打ちにすると GSM 期間の標高760〜3010m の山（604座中509座）が丸ごと稜線風欠測になり、
     最大の減点が消えてスコアが不当に高く出る（「データが無い→好条件」＝安全と逆方向）。
     - **欠けた面を別モデルから借りて埋めてはいけない**（実測で却下）。MSM が6面そろう日に
       900/800 を伏せて復元精度を比較した結果、この方式 0.76 m/s に対し icon補完 1.24 /
       gfs補完 1.32 m/s と**悪化**した。借りた値は別モデルなので隣の面との間に段差ができ、
       その段差（モデル間差 4〜7日目で平均 1.74 m/s）が埋めたい内挿誤差より大きいため。
       日照は「代替が無い」から借りる。風は自分の隣の面から内挿できるので前提が違う。
       同一モデル内の代替も不可（GSM の配信面は 1000/925/850/700/600/500 のみ）。
     - 残る副作用: GSM 期間は**風を弱めに見積もる系統的バイアス**。実測で
       760〜990m −0.15 / 990〜1460m −0.48 / 1460〜1950m −0.55 / **1950〜3010m −1.23 m/s**
       （③で3.6点分）。補正はせず、日付選択肢の「参考」表示と find-score.html で開示する。
  4. **雪・寒気（-10）**: `snowfall_sum` / `temperature_2m_min`。
- **欠測ガードは気象庁モデル由来の材料で数える**: 日照(気象庁)・天気コード・降水・稜線風が
  すべて欠測なら `score()` は `null` を返し一覧から外す。ここで補完日照を材料に数えると、
  気象庁モデルが全滅した地点が「①だけ減点＝80点前後のランクA」で最上位に出てしまう。
- 足切り: **稜線風 ≥18m/s（冬は ≥12m/s）** または 降水量 ≥10mm で「⚠ 慎重に判断が必要」表へ振り分け。
  冬判定は正式判定と同じ（月＋行動時間帯の山頂気温）。
  **これを入れる前は「冬・快晴・稜線風12m/s・最低-15℃」が 81点＝ランクA で最上位に出るのに、
  詳細ページの正式判定では C（冬モードは12m/sでC）だった。** 入口が安全と逆を向いていた。
  現在は同条件が 65点＝ランクB かつ足切り表送りになる。
- **各行に正式指数 A/B/C を併記する**。スコア（相対比較のふるい）と指数（行動可否の判定）は
  別物なので、両方を並べて食い違いにその場で気づけるようにする。
  find は視程を取得しないため **D4（視界不良）だけは計算できない**（主判定＋D1＋D2 を出す）。
- **降水確率は表示のみでスコアに入れない**（`score()` の戻り値 `pprob` は表示専用）。
  気象庁モデルに無いため汎用Forecast APIから別途取得しており、隣の降水量とはモデルが違う。
  異なるモデルの値を同じ点数に混ぜると意味が説明しづらくなるため、参考表示にとどめる。
- **限界（スコアが正式判定でない理由）**: スコア自体は**時間帯別の判定・発雷リスク・
  景色（眺望）・体感温度を含まない**日単位の相対指標。
  併記する指数は正式判定と同じロジックだが、視程が無いため D4 だけ欠ける。
  あくまで**エリア内の相対比較の入口**であり、実際の登山可否は各山の詳細ページで確認する。
- 表示: 天気列は「日照率ベース」で出す（daily.weather_code の24hmaxは表示主指標にしない。
  短時間の霧雨が晴主体の日を乗っ取り「曇りなのに日照97%」の矛盾を生むため）。降水リスクは降水列で示す。

## データソースと限界

- 予報: Open-Meteo API の**気象庁モデル**（前半=MSM 約5km / 後半=GSM。自動切替。
  切替日はモデルのラン時刻で前後するので固定日数で書かない）
  - 気象庁モデルに無い項目（降水確率・突風・CAPE/CIN・視程・積雪深・**0℃高度**）だけは
    汎用Forecast API（ベストマッチ合成）から補完し、時刻をキーにして貼り合わせる
  - **実測で確認した配信状況**（槍ヶ岳・11日間・MSM期間0-72h / GSM期間120h-）:

    | 変数 | 気象庁モデル | 扱い |
    |---|---|---|
    | `relative_humidity_2m` | 72/72・144/144 | JMA から取得 |
    | `temperature_850hPa` / `700hPa` / `500hPa` | 72/72・144/144 | JMA から取得。**500hPa も MSM 期間からある**（気圧面「風」が MSM 6面 / GSM 4面なのとは別） |
    | `freezing_level_height` | **全期間 null** | Forecast API から補完（264/264 取得可） |

## 追加した表示項目

- **雨雪判別**: `freezing_level_height` と山頂標高から 雪／みぞれ／雨 を降水セルに併記。
  0℃高度 < 山頂-100m → 雪 / > 山頂+200m → 雨 / 中間 → みぞれ。
  雪片は0℃高度から落下する間に融けるので、雨雪の境界は0℃高度より下に出る。
  **表示のみでA/B/C判定には使わない**。冬モードの「3h降水3mm以上=C」は水換算なので、
  1℃の雨と-5℃の雪が同じ「3.0mm」にしかならないのを表示側で補う。
- **上空の寒気**: 850/700/500hPa の気温を日中（9〜15時）平均で日別に出す。
  表示位置は**モデル間比較の下（出力の最後）**。行動判断に直結する表（見通し・詳細・モデル比較）を
  先に読ませ、気圧配置を自分で読むための参考値は後ろにまとめる。
  寒気の強さは冬型の荒れ方と夏の不安定度の両方を規定するが山頂気温では読めない。
  A/B/C判定には使わない（気圧配置を自分で読むための参考値）。
  - **MSM と GSM では配信される要素が違う**（実測）。GSM 期間に無いもの:
    `sunshine_duration` / `shortwave_radiation`、および気圧面 **900hPa・800hPa**。
    `cloud_cover`（低中高）・`weather_code`・`precipitation`・925/850/700/600hPa は全期間ある。
    要素を追加・利用するときは MSM 期間だけで確認せず、**必ず後半日の非null件数も数える**こと
- 予報範囲: 最長10日先（後半は精度が大きく低下、3日先までが実用域）
  - 気象庁モデル自体は11日目まで配信するが、11日目は昼過ぎでGSMが切れdaily集計値が丸ごと
    nullになる（hourlyから作り直しても部分日にしかならない）ため、完全にデータが揃う
    10日目までに表示を止めている
  - APIは実配信期間(11日)を超える期間を要求してもエラーにせず黙って null を並べるため、
    期間はコード側(`JMA_DAYS`)で制限する
- 直近実況もモデル解析値であり、観測所・アメダスの実測とは差がある
- 山岳の局地現象（滝雲、局地的突風、雷の正確な位置・時刻）は数値予報では表現不可
- モデル間比較（常時表示）で結果が割れる場合は予報の信頼度が低い
